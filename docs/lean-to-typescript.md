# Lean to TypeScript

Lean to TypeScript is TSLean's primary compiler. It supports a proof-oriented workflow for software that must run in TypeScript environments:

1. define executable behavior in Lean;
2. state and prove the properties that matter;
3. compile the admitted Lean program to TypeScript;
4. bind generated bytes to the elaborated program, proofs, compiler, and toolchain;
5. check that evidence before publication.

The current compiler has a strong artifact and test contract. It does not yet have a whole-compiler refinement theorem. Building that proof-carrying contract is the current priority.

## What a proof can guarantee

A theorem can guarantee the property it states for the modeled inputs and effects. It cannot guarantee an unstated requirement.

External behavior also needs assumptions. Examples include JavaScript engine conformance, cryptographic collision resistance, storage atomicity, clocks, and remote services. TSLean must keep these assumptions minimal, explicit, and outside theorem claims. A deployment must discharge them through exact platform evidence where possible.

## Command

```bash
tslean lean-to-ts \
  --project-root <lean-project> \
  --module <root-module> \
  --source <root-source-file> \
  --declaration <qualified-name> \
  --out-dir <generated-root> \
  --manifest <generated-root>/tslean.manifest.json
```

Repeat `--declaration` to compile more than one root.

| Option                  | Meaning                                            |
| ----------------------- | -------------------------------------------------- |
| `--project-root`        | Lean project root that Lake builds                 |
| `--module`              | Root Lean module loaded by the exporter            |
| `--source`              | Source file that owns the requested root module    |
| `--declaration`         | Qualified root declaration; repeatable             |
| `--out-dir`             | Owned generated package root                       |
| `--manifest`            | Manifest inside the generated root                 |
| `--check`               | Regenerate and compare without publishing          |
| `--require-attestation` | With `--check`, treat environment drift as failure |

The target project and TSLean must use the exact same Lean toolchain. The compiler does not guess across Lean versions.

## Compiler pipeline

Lean elaborates the requested module first. The exporter reads elaborated declarations and their complete reachable closure. It emits a semantic program rather than source text.

The TypeScript side then:

1. validates the semantic program and module graph;
2. rejects every reachable construct outside the admitted fragment;
3. assigns deterministic files, imports, aliases, and declarations;
4. emits one TypeScript module per Lean module;
5. emits a shared runtime module and source maps;
6. type-checks the complete generated tree;
7. publishes the tree and manifest transactionally.

Unsupported input produces a typed refusal before publication. The compiler emits no placeholder, guessed behavior, `any`, unsafe cast, or fallback implementation.

## Current fragment

The semantic IR admits a total, pure Lean fragment named `tslean-semantic-typed-v5`. The Lean
exporter and the semantic IR validator decide what the fragment admits, and they are the source of
truth. The compiler registry under `spec/lean-to-typescript/` binds the checked models to their
oracles and bounds. This document does not expand the fragment.

These families are admitted:

- `Bool`, `Nat` and `String`. `Nat` is a non-negative `bigint`, so subtraction truncates at zero
  through one shared helper.
- Type parameters on functions and on data types. The generated type parameters are positional, so
  a Lean binder name never decides a generated signature.
- Structures and finite inductives. A type whose namespace carries dot-notation methods becomes an
  immutable class; a type with no methods stays structural.
- Pattern matching on a user inductive, a structure, a `List`, an `Option` and an `Except`.
- `Option` and `Except`, each as one tagged union in the shared runtime module.
- `List`, as a readonly array, with the collection operations the runtime opcode registry names.
- Function values, as uncurried arrows at their full Lean arity. An abstraction may capture the
  binders in scope at its own position.
- Recursion Lean proved. A single structural recursion is re-verified against the emitted program;
  a mutual group or a well-founded measure is carried as Lean's own evidence, read from the
  kernel-checked unfolding equation, and no call may leave the recorded group.
- Modules and namespaces. One Lean module becomes one TypeScript file, and cross-module references
  become relative imports.

Method ownership comes from elaborated evidence. The exporter resolves a receiver against the
environment and records which parameter carries it; the compiler reads that record and never the
shape of a name.

Every runtime operation carries a stable opcode. `LEAN_RUNTIME_OPCODES` gives each one its Lean
symbol, the single TypeScript form the emitter produces, the kernel-checked model theorem that
relates them, and the assumption records that theorem closes over. The set is closed and total:
an operation outside it is refused rather than emitted.

Every admitted family must eventually carry:

- a Lean source semantics;
- a target JavaScript-model semantics;
- a refinement theorem or checkable certificate relation;
- deterministic lowering;
- generated-byte and toolchain binding;
- adversarial and differential tests.

Differential agreement finds counterexamples. It is not a proof.

## What the compiler refuses

A construct with no deterministic representation fails before publication, with a typed diagnostic
that names the declaration it was reading. The refused set includes `Int`, `Float`, the sized
integer types, `Char`, `Nat` division, matching on a `Nat`, string length and indexing, anything
that needs an instance dictionary, instance parameters, universe-polymorphic declarations,
dependent result types, dependent matches, matches on more than one discriminant, a `let` inside an
argument, `partial`, `unsafe`, `opaque`, `axiom`, `noncomputable`, and a declaration whose
executable form was replaced inside the target module closure.

Two audits run over the whole reachable closure. A declaration that rests on an axiom outside
`propext`, `Classical.choice` and `Quot.sound` is refused, and so is one whose unfolding proof
depends on `sorry`. A root's boundary is monomorphic: a polymorphic root, or one whose parameter or
result has no data image, is refused rather than given a decoder a caller cannot use.

## Generated package

A compilation emits:

- one TypeScript module for each contributing Lean module;
- one shared generated runtime module;
- one source map per generated Lean module;
- one manifest covering the package.

The manifest binds the selected declarations, semantic program, transitive Lean module closure, available source files, exporter and compiler sources, exact Lean and TypeScript toolchains, package layout, generated modules, runtime, and source maps.

Generation rechecks every bound input before publication. Input drift fails rather than producing a mixed artifact.

## Publication

The publisher owns one output root and one manifest inside that root.

It refuses output that overlaps compiler inputs, symlinked ancestors or children, manifests outside the output root, aliased destinations, changed filesystem identity, unowned stale files, and unsynchronized concurrent writers.

Shrinking a tree removes only files owned by the prior manifest. A failed publication restores the prior tree, including files the new tree intended to delete.

## Runtime boundaries

Generated decoders validate external values. They do not cast data into Lean-derived types.

Each external effect must enter through a modeled port. Generated pure code must not gain ambient filesystem, network, clock, random, credential, or storage authority.

## Current evidence

The Lean 4.33.1 repository gate includes:

- 1,932 passing tests and 10 explicit todo tests;
- 7,587 differential vectors;
- a complete 184-job Lean build;
- four executable target checks;
- strict generated-tree TypeScript compilation;
- deterministic double generation;
- source-map consumer validation;
- package-consumer tests;
- transaction, rollback, shrink, collision, and path-isolation tests;
- trusted-base checks for generated internal semantics.

The placement example compares all 4,096 inputs in its finite domain. That result applies only to that example and domain.

## Proof-carrying roadmap

The remaining proof work is explicit:

1. define source and target operational semantics for the admitted IR;
2. prove each lowering rule preserves results and modeled effects;
3. generate a certificate that names the exact IR and generated modules;
4. check the certificate before publication;
5. bind certificate, proofs, compiler, runtime, and generated bytes in the manifest;
6. minimize and publish the trusted computing base;
7. validate the system on Agent Core as the first substantial consumer.

A construct is not admitted to the proved fragment until its lowering obligation is discharged.

## Nonclaims

The compiler does not currently claim full Lean support, whole-compiler formal correctness, proof of JavaScript engine conformance, or application correctness from compilation alone.

Successful compilation establishes the checked artifact contract. Future proof certificates will additionally establish the named refinement properties for the admitted fragment and explicit model assumptions.
