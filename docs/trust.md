# Compiler Trust Policy

## Gates enforced now

The current release gate establishes these facts:

- Lean-to-TypeScript elaborates the selected Lean declarations and rejects unsupported reachable IR before publication.
- Lean-to-TypeScript type-checks the complete generated tree and publishes it with a content-bound manifest through one transaction.
- TypeScript-to-Lean `--strict` rejects every degradation that the current compiler records before it writes source or build files.
- The CLI exposes no generated proof-placeholder path. Proofs use hand-authored Lean and the normal Lean gate.
- The JavaScript and refinement audits check their registered theorem sets against the closed axiom allowlist.
- Every inline runtime opcode's emitted form is printed by the compiler and compared byte for byte with the form the Lean registry states, at generation, at package verification, and in the semantics gate.
- The semantics gate reads each dispatch it joins from the declaration and the value that declaration discriminates, and its joined counts and its own script are pinned and hashed in the evidence manifest.
- Differential tests are reported as counterexample searches, not refinement proofs.
- Evidence freshness depends on content and toolchain identity, not a Git branch name.

These gates do not establish a whole-compiler refinement theorem. Non-strict
TypeScript-to-Lean output can contain reported degradation. Raw Lean syntax nodes and
source scanners still exist in the TypeScript-to-Lean compiler. The present audits cover their
registered sets, not every future program or analysis.

## Trusted computing base

Everything a generated package's correctness claim leans on, whether or not a proof covers it. The
pipeline is: the Lean kernel elaborates, `Export.lean` emits a semantic program, `ir.ts` re-validates
it, `emitter.ts` plans and builds TypeScript syntax, the TypeScript printer prints, the emitted tree
is type-checked, the manifest and digests bind, and the publication transaction publishes. Two
TypeScript compilers appear in that list and the split is deliberate: everything that reads or
checks TypeScript reads through 7.0.2, and only the construction and printing of emitted syntax —
which has to carry Lean docstrings as comments — holds the 6.0.2 pin (**7**, **17**, **24**). The
kernel, the JavaScript model and the refinement proofs are proof-checked. The exporter, the decoder,
the emitter, the printer, the compilers, the manifest plumbing, the gates and the probes are trusted
code with mechanical cross-checks, listed here with what checks them and what is left. Counts in
this table are the ones a gate prints or the evidence manifest pins; a residual names the
requirement below that closes it.

## Required before a proof-carrying claim

The following requirements are under construction. No artifact may claim the
proof-carrying guarantee until every applicable requirement is enforced.

1. Compilation is total over its declared input. Failure returns typed diagnostics and never becomes a placeholder or guessed implementation.
2. Printed code comes from typed syntax nodes. No raw-source node bypasses the semantic IR and printer.
3. Placeholder and trusted-base audits operate on parsed semantic structure, not source-text patterns.
4. Comment content cannot introduce declarations or change generated semantics.
5. The compiler fabricates no language instances or laws.
6. Platform behavior enters through an explicit capability, formal model, or named conditional runtime assumption.
7. Every exported theorem passes its transitive axiom gate.
8. Every analysis has a proved or checked complexity bound and an adversarial scaling oracle.
9. Every admitted Lean-to-TypeScript operation names its source semantics, target semantics, lowering theorem, emitted runtime body, and exact assumptions.
10. Generation fails when any reachable operation lacks its proof or certificate record.
11. The manifest binds semantic IR, proofs, certificates, compiler, runtime, generated bytes, source maps, and exact toolchains.
12. External assumptions are obligations to discharge through a certified adapter, runtime proof, or exact conformance evidence.
13. Publication requires every applicable proof, certificate, assumption record, and freshness check.
14. Synthesis accepts a candidate only when every proof and model obligation is closed.
15. Rejected candidates retain machine-readable diagnostics and no deployment authority.
16. The nominal class representation a behaviour-carrying type compiles to is modeled by the lowering the refinement theorem covers, or the compiler refuses that type.
17. Every engine assumption is discharged on the engine that runs the published package, by evidence bound to that engine's identity, not only on the machine that compiled it.
18. Probe expectations are generated from the Lean model, so an expectation cannot agree with an engine the model contradicts.
19. Every program whose evaluation can produce a list discharges the array-length bound its refinement rows assume, or the target semantics models the failure that bound rules out.
20. Every emitted body shape is one the modeled lowering produces. The statement forms `emitReturn` builds are: `Compile.returnBody` lowers the `const` run, the statement-form `if` and the tag dispatch with its payload bound by `const`s, and `Preservation.ifThenBody` and `Preservation.branchBody` prove both refine the source, for every payload-carrying union whose values are variants — `JsonValue`, `Option`, `Except` and every declared `enum`. What remains is a `match` on a `List` in return position, which needs the array-length tests and the element and `slice` reads as a third dispatch shape; a payload-carrying `match` in argument position, which needs the substitution of a payload read into an arm that `emitMatchExpression` performs; and a `match` on a one-constructor structure, which needs `Source.eval` to destructure a `record` value at all. Each of the three is refused by name in the model — `Fault.listMatch`, `Fault.substitutedMatch`, `Fault.structureMatch` — while `emitter.ts` still prints all three, so what those names buy is a countable boundary, not a closed one: this requirement is discharged only when the model carries the shape or the emitter refuses it.
21. Every host boundary a published package declares carries conformance evidence that the substrate's binding satisfies the equation `HostSubstrate` states, bound to that substrate's identity, and generation refuses a boundary with no such row.
22. `ByteArray` and the two map types are computed with only once `Uint8Array` and `Map` are modeled as objects carrying the internal slots ECMA-262 gives them, with the framing and allocation lemmas the dense-array representation already has; until then the decoder refuses a program that computes with one.
23. The Lean operations whose Lean meaning and JavaScript meaning differ are refused by name with the semantic reason, not silently mapped: `Int.ediv`/`Int.emod` (Lean's remainder is non-negative, BigInt's takes the dividend's sign — `Int.tdiv`/`Int.tmod` are the admitted pair), `String.lt` (Lean orders code points, `<` orders UTF-16 code units, and they disagree for an astral character against U+E000..U+FFFF), `String.get` and `String.Pos` (Lean positions are UTF-8 byte offsets, JavaScript indices are UTF-16 code units), and `UInt8` arithmetic (wrapping, which needs a modular opcode family).
24. One compiler both reads and emits. Emission holds a 6.0.2 pin only because 7.0.2 cannot attach a comment to constructed syntax; when it can, the pin and the seam module go, and the compiler that type-checks a generated package is the one that printed it.
